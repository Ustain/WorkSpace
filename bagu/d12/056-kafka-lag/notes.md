# 56. 积压排查与扩容 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **消费速度 < 生产速度**。指标：Consumer Lag = HW - 已提交 offset。

先止血再根因，别一上来改代码重构。

## 2. 核心机制

**排查顺序**

1. 看 Lag 是一个分区还是全部：单分区可能热 key/热点分区。
2. 看消费者是否在 rebalance、是否频繁掉组。
3. 看处理耗时：下游 DB/RPC 慢。
4. 看生产是否突增。
5. 看 ISR、磁盘、Broker 是否也慢（少见但要排除）。

**提高消费**

- 加消费者，但 **≤ 分区数**。
- 优化处理（批量写库、降 RPC）。
- 临时加分区：**会打乱 key 顺序**，且老消息不会自动均分到新分区。
- 独立扩消费组做分流（新组从 latest 只追新的，慎用）。

**卡点**

- 加消费者超分区数没用。
- 单分区积压只能垂直优化或拆 key 重分区（未来数据）。

## 3. 生产坑 / 反例

- **积压时从头消费另一个组** 当修复：会打爆下游。
- **扩分区当银弹**：历史 Lag 仍在老分区。
- **消费里同步重试死循环**：Lag 只增不减。

## 4. 60 秒口述

> 积压看 Lag。先分清是下游慢、rebalance 还是生产突增。加消费者不能超过分区数；单分区热点要拆 key 或优化处理。  
> 扩分区只帮以后的并行，会改变顺序，历史消息还在原分区。应急可以降级非核心逻辑、批量写、暂时丢弃可丢失的监控流。
