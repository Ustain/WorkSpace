# 13. 行锁、间隙锁、next-key · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **InnoDB 当前读怎么锁索引**。快照读基本不走这套。

- **行锁 Record Lock**：锁 **索引记录** 本身（不是锁「行的物理位置」那么简单）。
- **间隙锁 Gap Lock**：锁 **两条索引记录之间的空隙**，禁止在这个区间插入。
- **next-key**：Record + 前面那个 Gap，InnoDB RR 默认的范围锁。

和「表锁」比：InnoDB 普通 DML 是行级；表级还有意向锁（题 15）。

## 2. 核心机制，卡在哪会出问题？

**锁在索引上**

没有合适索引时，当前读可能退化成 **锁很多行甚至当间隙全锁**。这是生产死锁/锁等待的根。

**举例（主键 id：1, 5, 10）**

```sql
SELECT * FROM t WHERE id = 5 FOR UPDATE;     -- 等值，常是行锁（唯一索引）
SELECT * FROM t WHERE id > 5 FOR UPDATE;     -- RR：锁 (5,10]、(10,+∞) 这类 next-key
INSERT INTO t VALUES (7);                    -- 掉进间隙，被 gap 挡住
```

- **唯一索引等值命中**：通常只要记录锁。
- **唯一索引等值未命中**：锁间隙，防幻影插入。
- **非唯一索引 / 范围**：next-key，间隙更大。

**RC vs RR（必说）**

- RR：有 gap / next-key，防当前读幻读。
- RC：通常 **没有 gap**（有半一致读等例外），插入更自由，死锁更少，幻读可能发生。

**卡点**

- 间隙是左开右闭的 next-key 直觉：锁的是「记录 + 前面缝」，不是锁一行的字段值。
- 两个事务锁相邻间隙再互相插/更，最容易死锁。

## 3. 生产坑 / 反例

- **「间隙锁锁的是行」**——锁的是缝，缝里还没有行。
- **WHERE 条件没走索引**：RR 下可能锁全表所有间隙，并发插不进去。
- **导入数据时 RR + 大范围 FOR UPDATE**：插入被间隙堵住，看起来像「数据库卡住」。

## 4. 60 秒口述

> InnoDB 当前读锁在索引上：行锁锁记录，间隙锁锁两条记录之间的缝，next-key 是记录加前面缝，RR 默认用它防插入型幻读。  
> 唯一索引等值命中往往只锁行；范围和非唯一索引会锁一大段间隙。RC 基本不加间隙锁，所以死锁少但可能幻读。  
> 生产上当前读必须走准索引，否则 RR 会把间隙锁满。
