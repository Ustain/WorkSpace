# 15. 意向锁与锁粒度 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **表级意向 + 行级真实锁** 怎么共存。意向锁不是用来锁行数据的，是 **快速判断「这表里有没有行锁」**。

- **IS（意向共享）**：我等会儿要加行级 S 锁。
- **IX（意向排他）**：我等会儿要加行级 X 锁。
- 真正互斥发生在：**表锁 vs 意向**、以及 **同行的行锁**。

和「行锁」比：行锁保护记录；意向锁保护「能不能升级成表锁」这条通路。

## 2. 核心机制，卡在哪会出问题？

**为什么需要**

若没有意向锁，事务 A 要 `LOCK TABLES t WRITE`（表 X 锁），引擎得扫全表看有没有行锁，太贵。有了 IX：表上已有 IX，说明里面有人行锁，表 X 立刻冲突。

**兼容（口试记结论）**

| | IS | IX | S（表） | X（表） |
|--|:--:|:--:|:------:|:------:|
| IS | ✓ | ✓ | ✓ | ✗ |
| IX | ✓ | ✓ | ✗ | ✗ |
| S | ✓ | ✗ | ✓ | ✗ |
| X | ✗ | ✗ | ✗ | ✗ |

所以：很多事务同时对 **不同行** 加 IX + 行 X，互相兼容。有人要整表 S/X 才会和 IX 撞。

**InnoDB 锁粒度直觉**

- 普通 DML：表上 IX + 索引上行/间隙锁。
- `LOCK TABLES`、部分 DDL、`AUTO-INC` 等才走到更粗的表级。
- 锁粒度越粗并发越差；越细死锁检测和内存开销越大。

**卡点**

- 面试别说「意向锁会锁住行」。它锁的是表，而且几乎总是立刻加上。
- `SHOW ENGINE INNODB STATUS` 里常见 `IX`，这是正常现象，不代表表被独占。

## 3. 生产坑 / 反例

- **线上乱用 `LOCK TABLES`**：和 InnoDB 行锁模型打架，把并发打成串行。
- **大事务 + 很多行 X**：意向没问题，但行锁太多，锁内存涨、死锁多。
- **DDL 等 MDL**：那是 Server 层元数据锁，和意向锁不是同一个东西；ALTER 卡住常是 MDL 等长查询。

## 4. 60 秒口述

> 意向锁是表级标记：IS 表示即将行级共享，IX 表示即将行级排他。它用来让表锁不必扫全表就能知道里面有没有行锁。  
> 多个事务对不同行加 IX 是兼容的；只有有人要整表锁才会和意向冲突。InnoDB 日常是表 IX 加行锁。别把意向锁讲成行锁，也别和 MDL 混为一谈。
