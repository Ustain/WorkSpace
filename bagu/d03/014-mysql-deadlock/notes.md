# 14. 死锁成因与排查 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **行锁/间隙锁形成环等待**。InnoDB 有死锁检测，会回滚代价较小的那个事务，报 `1213 Deadlock`。

和「锁等待超时」不同：超时是等不到（`innodb_lock_wait_timeout`，默认 50s）；死锁是互相等，检测后立刻回滚一方。

## 2. 核心机制，卡在哪会出问题？

**成因（面试画环）**

1. 事务 A 锁住行 1，要行 2。
2. 事务 B 锁住行 2，要行 1。
3. 形成环 → 死锁。

间隙锁会让环更隐蔽：A 锁间隙，B 锁另一段，双方再 INSERT 进对方间隙。

**InnoDB 怎么处理**

- 后台检测等待图有没有环。
- 回滚 undo 量更小的事务（不是简单「后开始的」）。
- 应用收到 1213，**整单重试** 才是正确姿势。

**排查顺序**

1. 应用日志抓 `Deadlock found when trying to get lock`。
2. `SHOW ENGINE INNODB STATUS` → `LATEST DETECTED DEADLOCK`：看两个事务的 SQL、锁类型（RECORD/GAP）、索引。
3. 8.0 可开 `innodb_print_all_deadlocks` 或 performance_schema 锁表。
4. 对照 SQL：是不是 **加锁顺序不一致**、有没有 **先查后改漏索引**、RR 间隙是不是太大。

**卡点**

- 死锁信息只保留最近一次，线上要尽快捞。
- 业务「捕获后忽略」→ 账不平；必须重试或告警。

## 3. 生产坑 / 反例

- **加锁顺序不统一**：批量更新按 id 排序再更新，环会少很多。
- **SELECT 再 UPDATE 两段事务**：改成一条 `UPDATE ... WHERE`，或 `SELECT FOR UPDATE` 且顺序固定。
- **RR 改 RC**：gap 减少，死锁下降，但要接受不可重复读/幻读语义。
- **索引缺失**：锁升级到很多行，死锁概率暴涨。

## 4. 60 秒口述

> 死锁是多个事务持锁再要对方的锁，等待图成环。InnoDB 检测到就回滚代价小的那个，返回 1213，应用必须重试整笔业务。  
> 排查看 INNODB STATUS 里最近死锁，对 SQL、索引、是行锁还是间隙锁。根治是统一加锁顺序、补索引、缩短事务、必要时 RC，而不是把超时调大。
