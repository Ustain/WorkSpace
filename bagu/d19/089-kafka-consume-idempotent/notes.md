# 89. 消费端幂等落地 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **至少一次消费怎么落库只一次**。Kafka EOS 不替代这题。

## 2. 核心机制

**最小闭环**

1. 消息带 `event_id` / 业务单号。
2. 表 `consume_log(event_id PRIMARY KEY)` 或业务表唯一键。
3. **本地事务**：写业务 + 写去重（或先插去重成功再做事，看失败补偿）。
4. 成功再提交 Kafka offset。

**状态机**

- 订单 `CREATED → PAID`，重复支付事件看到已是 PAID 直接成功。

**乱序**

- 幂等不解决乱序。要版本号、忽略过期事件。

**卡点**

- 去重表与业务不在同一库：又变成分布式事务。优先同库。
- 只 Redis 去重：重启或淘汰会重复下单。

## 3. 生产坑 / 反例

- **先提交 offset 再写库** → 丢。
- **先写库再交 offset 但不幂等** → 重复。
- **用 offset 当去重键**：换组、重放会乱。

## 4. 60 秒口述

> 消费端幂等靠业务唯一键或去重表，最好和业务同一本地事务，成功再交 offset。重复消息第二次唯一冲突就跳过。  
> 不要用 Redis 当资金去重，不要用 offset 当业务 id。乱序要另做版本。
