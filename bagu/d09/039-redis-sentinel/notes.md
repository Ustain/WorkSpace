# 39. 哨兵原理与脑裂 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **Redis 主从高可用**。哨兵是一组进程，监控主库，挂了把从库提升成新主，并让其他从去复制新主。

和 Cluster 比：哨兵管 **故障转移**，数据仍是 **一份全量**（主从复制）；Cluster 才分槽。

## 2. 核心机制

1. 哨兵定期 PING 主从。
2. 主观下线：一个哨兵觉得主挂了。
3. 客观下线：达到 **quorum** 个哨兵同意。
4. 选举一个哨兵 leader（Raft 味道的多数派）。
5. leader 在从库里挑（复制偏移量等），`SLAVEOF NO ONE` 提升。
6. 通知客户端新主（客户端要能订阅或轮询 sentinel）。

**脑裂**

- 旧主网络分区里还活着，客户端仍写旧主；另一边选出新主。
- 分区恢复后，旧主变成从，**全量/部分数据被同步覆盖丢掉**。

**怎么减**

- `min-replicas-to-write` / `min-replicas-max-lag`：副本不够就拒绝写。
- 客户端只从哨兵取当前主，不要写死 IP。
- 多数派哨兵（至少 3），跨机房部署要小心网络抖动误切。

## 3. 生产坑 / 反例

- **两个哨兵**：没有可靠多数，脑裂/切不了。
- **哨兵和 Redis 堆同一台**：机器挂，监控一起没。
- **切换成功但连接池仍连旧主**：应用要处理只读错误和重连。

## 4. 60 秒口述

> 哨兵监控主从，多数派确认主挂后选 leader，提升最健康的从库。它解决自动故障转移，不分片。  
> 脑裂是旧主分区还在收写，恢复后被新主覆盖丢数据。哨兵要奇数个，写要限制最少副本，客户端跟着哨兵走新主。
