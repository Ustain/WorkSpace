# 40. Cluster 槽位、迁移、MOVED · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **Redis 官方分片**。不是一致性哈希直接算节点，而是 **16384 个槽（0～16383）**，槽再分配给节点。

`slot = CRC16(key) % 16384`。带 `hash tag` `{user:100}.name` 按括号里算，保证同一用户落到同槽。

## 2. 核心机制

**拓扑**

- 每个主负责一段槽，主可以有从。
- 客户端最好是 **智能客户端**：缓存槽表，直连对应节点。

**MOVED / ASK**

- **MOVED**：槽已经稳定在另一个节点，客户端更新槽表再去。
- **ASK**：槽正在迁移，这一次去目标节点，**先 ASK 再命令**，槽表暂不永久改。

**迁移**

- 槽从源节点迁到目标：key 一个个搬。
- 迁移中读到源没有的 key，源让客户端 ASK 到目标。
- 迁移期间该槽延迟和失败会升高。

**卡点**

- 多 key 命令（`MGET`、事务、Lua）要求 **keys 在同一槽**，否则报错。
- 没有中心代理时，客户端必须处理重定向。

## 3. 生产坑 / 反例

- **「Cluster 用一致性哈希」**——错，是 16384 槽。
- **热槽**：一个 key 极热，槽迁走也没用，要拆 key。
- **big key 迁槽**：迁移阻塞。
- **集群内用事务当跨 slot 原子**——做不到。

## 4. 60 秒口述

> Cluster 把 16384 槽分给各主，key 用 CRC16 取模进槽。客户端连错节点会收到 MOVED 更新槽表；迁移中是 ASK。  
> 多 key 必须同槽，常用 hash tag。它解决容量和部分故障隔离，解决不了热 key，也没有跨槽事务。
