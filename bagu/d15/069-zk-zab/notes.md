# 69. ZooKeeper 解决什么、ZAB 直觉 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **分布式协调**：配置、选主、分布式锁、临时节点感知存活。**不是业务数据库**。

ZAB（Zookeeper Atomic Broadcast）保证副本 **顺序广播**，看起来像单一副本。

## 2. 核心机制

- 集群选 **Leader**，写走 Leader，再广播给 Follower。
- 多数派（过半）ack 才提交 → **CP**：分区时可能不可写，但能避免脑裂双主。
- 数据是小 znode 树，有 **watch**、临时节点（会话断了节点没）。

**ZAB 直觉**

- 崩溃恢复：选新 Leader，对齐 epoch/zxid，保证已提交的不丢、未提交的不乱。
- 广播阶段：Proposal → ack → commit，全局有序。

**卡点**

- 必须奇数节点（3/5），过半存活。
- 写延迟受多数派磁盘/网络限制。
- 数据量要小，watch 风暴要防。

## 3. 生产坑 / 反例

- **当 MySQL 用存大量业务** → 拖死。
- **2 个节点**：没有过半容错。
- **临时节点当锁但不处理连接闪断**：误解锁。

## 4. 60 秒口述

> ZK 做协调：选主、锁、配置、成员感知，用 ZAB 让写有序且过半提交，偏 CP。临时节点和 watch 是特色。  
> 不要当业务库。集群奇数台，数据保持小。Kafka 老版本、很多中间件都靠它选主。
