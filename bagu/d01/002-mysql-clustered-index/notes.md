# 2. 聚簇索引、二级索引、回表 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **InnoDB 表数据怎么和 B+ 索引绑在一起**，不是「要不要建索引」。

- **InnoDB 聚簇**：整张表就是主键那棵 B+Tree，**叶子 = 完整行**。按主键查，降到叶就有所有列。
- **MyISAM**：索引和数据分开。一级、二级索引叶子都是 **数据文件里的行地址（指针）**，没有「先拿主键再进聚簇」这一跳。
- **二级索引（辅助索引）**：另一棵更瘦的 B+Tree。叶子 **不存整行**，只存 `索引列值 + 主键值`（没有显式主键时用隐藏 `ROW_ID`）。主键就是回表的通行证。

## 2. 核心机制，卡在哪会出问题？

**聚簇索引**

- 一张 InnoDB 表 **只有一棵聚簇索引**（通常就是主键）。
- 叶子页里按主键有序存 **整行数据**；非叶子只当路标。
- 行物理顺序 ≈ 主键顺序。主键选不好（随机 UUID、频繁更新）会导致页分裂、碎片，二级索引也要跟着改。

**二级索引 + 回表**

典型 SQL：`SELECT * FROM t WHERE name = 'a'`，`name` 上有普通索引。

1. 在 **name 索引树** 上定位 `name='a'`，叶子拿到 **主键 id**（可能多条）。
2. 用每个主键再去 **聚簇索引树** 查整行 → 这一步叫 **回表**。
3. 所以 `SELECT *` 往往 **两棵树、多次随机 IO**。

若 `SELECT id, name`，所需列都在 name 索引叶子里 → **不回表**（下一题覆盖索引）。

**常见错答**

- 二级索引叶子存「行指针/物理地址」——InnoDB 存的是 **主键**，不是 MyISAM 那种地址。
- 以为可以有多棵聚簇索引——只有一棵；其它都是二级。

## 3. 生产坑 / 反例

- **宽二级索引 + SELECT \***：命中很多行时，每条都要回表，随机 IO 爆炸。改 `SELECT` 列、建覆盖索引、或让查询只走聚簇（按主键查）。
- **主键用 UUID**：插入随机、页分裂多；二级索引叶子里的主键也要跟着搬。
- **没有主键**：InnoDB 用隐藏 `ROW_ID` 当聚簇键，你不可控，仍建议显式主键。

## 4. 60 秒口述

> InnoDB 表本身就是主键那棵 B+Tree，叫聚簇索引，叶子存整行。  
> 其它索引是二级索引，叶子只存「索引列 + 主键」，不存完整行。  
> 用二级索引查且还要其它列时，先在这棵树上找到主键，再拿主键去聚簇树取整行，叫回表，所以 `SELECT *` 经常两棵树。  
> MyISAM 相反，索引叶子存行地址。生产上要避免宽索引 + SELECT * 导致大量回表，主键也尽量递增、别乱用随机 UUID。
