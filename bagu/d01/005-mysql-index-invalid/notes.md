# 5. 索引失效常见原因 · 口试

## 1. 属于哪块？和相邻方案差在哪？

「失效」口语上指 **优化器没用上索引 / 用了但效果差**，不是索引被删了。根因多是：**破坏了 B+Tree 有序定位**，或 **全表扫更划算**。

和题 4 最左前缀重叠的部分不重复背，这题补 **SQL 写法 + 优化器选择**。

## 2. 核心机制：常见失效场景

**① 违反最左前缀（题 4）**

`INDEX(a,b,c)` 却 `WHERE b=1` → 用不上。

**② 对索引列做函数 / 计算**

```sql
WHERE YEAR(create_time) = 2024   -- 列被包在函数里
WHERE id + 1 = 5                 -- 对列运算
```

索引存的是 `create_time` 原值，不是 `YEAR(...)`。引擎无法按原索引有序定位 → 往往全表扫。  
改法：`create_time >= '2024-01-01' AND create_time < '2025-01-01'`。

**③ 隐式类型转换**

```sql
-- phone 是 VARCHAR，索引在 phone 上
WHERE phone = 13800138000        -- 数字，可能把列转成数字再比
```

规则记：**字符串列与数字比，常转列** → 索引废。应 `WHERE phone = '13800138000'`。  
（数字列与字符串比，常转常量，一般还能用索引。）

**④ LIKE 左模糊 / 全模糊**

```sql
WHERE name LIKE '%张%'   -- 前缀未知，无法二分
WHERE name LIKE '%张'    -- 同上
WHERE name LIKE '张%'    -- ✓ 最左前缀固定，可用
```

**⑤ OR 导致全表扫**

```sql
WHERE a = 1 OR b = 2
```

若 `a` 有索引、`b` 没有，优化器常 **整句走全表**（除非 index merge，看版本与数据）。  
改法：拆 UNION、或给 b 也建索引、或改写 SQL。

**⑥ 优化器认为全表更快**

- 表很小、命中行数占比很高（如 >20%～30%，无固定阈值）
- 统计信息过期，错估 rows
- 区分度极低的列（如性别 status 只有 0/1）

索引还在，**主动选** 全表扫。用 `EXPLAIN` 看 `type=ALL` 不一定是 SQL 写错。

**⑦ 不等于 / NOT / NULL（谨慎背）**

`!=`、`<>`、`NOT IN`、`IS NOT NULL` **有时** 仍走索引（看选择性、版本）。口试说：**高选择性可能走 range；低选择性可能全表**，别背「一定失效」。

**⑧ 字符集 / 排序规则不一致**

两列 JOIN 或比较时 collation 不同，可能转函数 → 索引不能用。

## 3. 生产坑 / 反例

- **只背八股不 EXPLAIN**：很多是优化器选择，不是索引坏了；先 `EXPLAIN ANALYZE`。
- **「对索引列用函数一定失效」**：生成列 + 索引（`date_col` 上建 `(YEAR(d))` 的函数索引）可破——知道即可，口试提一句加分。
- **隐式转换最难查**：Java/MyBatis 传参类型和列类型不一致，线上慢 SQL 常见根因。
- **最左前缀 + 范围**：`a>1 AND b=2`，b 可能用 ICP 过滤但 **不能当定位**，别和「b 完全失效」混为一谈。

## 4. 60 秒口述

> 索引失效指没用上或用得差。常见：违反最左前缀；对列做函数或运算；字符串列隐式转数字；LIKE 以 % 开头；OR 一边无索引；优化器判断全表更省；collation 不一致。排查用 EXPLAIN，改写 SQL 让列「裸奔」出现在条件里，保证类型一致，LIKE 尽量左固定。不等于是否失效看选择性，别绝对化。
