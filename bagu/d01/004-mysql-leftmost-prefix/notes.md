# 4. 联合索引与最左前缀 · 口试

## 1. 属于哪块？和相邻方案差在哪？

**多个列组成一棵 B+Tree 索引**，叶子按 **(a, b, c) 字典序** 排列，不是每列各一棵独立的树。

- **联合索引** `INDEX(a, b, c)`：排序规则是先比 a，a 相同再比 b，b 相同再比 c。
- **最左前缀**：匹配必须从 **最左边那列开始、中间不能断**。能用上 a；能用 a,b；能用 a,b,c；**单独 b 或 c 用不上这棵索引**（除非有别的单列索引）。

和「多个单列索引」不同：`(a,b,c)` 一棵树的排序键是 **组合键**，不是三棵独立树。

## 2. 核心机制，卡在哪会出问题？

**叶子怎么排（字典序）**

```
INDEX(name, age)

(李四, 20) → id=2
(李四, 25) → id=5
(王五, 30) → id=3
(张三, 18) → id=1
(张三, 20) → id=4
```

先按 name 排序，name 相同再按 age。像电话簿：先姓后名。

**最左前缀 = 从组合键左边连续用列**

| SQL 条件 | 能否用 INDEX(a,b,c) | 用到哪 |
|----------|---------------------|--------|
| `a=1` | ✓ | a |
| `a=1 AND b=2` | ✓ | a,b |
| `a=1 AND b=2 AND c=3` | ✓ | a,b,c |
| `a=1 AND c=3` | 部分 ✓ | 只 a（c 跳列，b 断了） |
| `b=2` | ✗ | 无最左 a |
| `b=2 AND c=3` | ✗ | 无最左 a |
| `a>1 AND b=2` | 部分 ✓ | a 范围后 b 往往用不了（见下） |

**范围查询截断后面的列**

`WHERE a > 1 AND b = 2`：a 用 **范围** 扫描后，**b 通常无法再用索引有序性**（优化器/版本细节有 ICP 等例外，口试说「范围列之后的列难用」即可）。

**为什么必须最左**

B+Tree 按 **(a,b,c) 整体** 排序。没有 a 的值，b 在全局不是有序的——`(李四,20)` 和 `(张三,20)` 里 age=20 散在各处，不能跳过 a 直接二分 age。

## 3. 生产坑 / 反例

- **列顺序写反**：查询 `WHERE status=? ORDER BY created_at`，索引 `(created_at, status)` 不如 `(status, created_at)`。
- **以为 `(a,b,c)` 能单独优化 `WHERE b=?`**——不能，除非再建 `(b)` 或 `(b,c)`。
- **跳列**：`WHERE a=1 AND c=3`，c 用不上（b 缺失）；可 ICP 在索引层过滤 c，但 **c 不参与定位**。
- **最左前缀 ≠ 必须把 a 写在 WHERE 第一位**：`WHERE b=1 AND a=2` 优化器重排后仍能用 a（等值都出现时）。

## 4. 60 秒口述

> 联合索引 (a,b,c) 是一棵 B+Tree，按 a→b→c 字典序排。最左前缀：必须从 a 开始连续匹配，a 能用、b 在 a 定后才能用、c 在 b 定后才能用。单独查 b 用不上 (a,b,c)。范围查 a 后，后面的 b 往往用不上索引排序。建索引时把 **最常过滤、区分度高、常一起查** 的列放左边，按真实 SQL 设计顺序。
