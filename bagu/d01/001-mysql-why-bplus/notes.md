# 1. 为什么用 B+Tree 而不是 Hash/B-Tree · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **InnoDB 怎么在磁盘上组织索引**，不是 SQL 语法，也不是缓存。

查询类型（等值 `=`、范围 `>` / `BETWEEN` / `ORDER BY`）一直都在。没有合适索引时只能 **全表扫**，O(n) 次页 IO。

- **Hash**：等值 O(1)，但哈希打散后相邻 key 不相邻，**不能范围扫、不能排序**。MEMORY 引擎、InnoDB 自适应哈希只补等值。
- **B 树**：等值、范围都能做，但内部节点也存行 → 同一页路标少 → 树更高；范围是中序跨层，随机 IO。适合内存，不适合按页读盘。
- **B+**：内部只当路标，数据全在叶子且叶子链表。等值走树高次随机 IO；范围先下降再顺序扫叶。

## 2. 核心机制，卡在哪会出问题？

一页 16KB。内部节点：`分隔 key + 子页指针`。叶子：全部索引记录（聚簇=整行，二级=key+主键），页内有序，页间双向链表。

- **等值**：根起每层页内二分，只选一个孩子，读到叶。IO ≈ 树高（常 3～4）。有序才能每层丢掉其余分支。
- **范围**：同样下降定位左端叶子，再顺着链表扫到右端。链表断了或当成 B 树中序跳，范围就会变成随机 IO。
- **矮**：扇出大（一页上千路标）。内部若塞行，扇出塌掉，树变高，等值 IO 变多。

## 3. 生产坑 / 反例

- **范围太大**：叶子链几乎覆盖全表，B+ 救不了选择性极差的条件，看起来走索引其实接近全扫。
- **不要说 Hash 能范围查**；也不要说「有了 B+ 任何查询都不扫全表」。
- 等值极热路径上，InnoDB 还有自适应 Hash，那是 B+ 之上的加速，不是替代。

## 4. 60 秒口述

> InnoDB 用 B+Tree 当索引，是为了在磁盘上同时扛等值和范围，避免动不动全表扫。  
> Hash 等值快但无序，范围和排序废掉。B 树能两种查询，但内部节点存行，一页路标少、树更高，范围还要跨层中序，随机 IO 多。  
> B+ 内部只放 key 和指针，扇出大、树矮；所有数据在叶子，叶子串成链表。等值从根降到叶，IO 是树高；范围先降到左端再顺序扫叶。  
> 坑：条件选择性很差时，扫叶子≈扫全表，索引不是万能的。
