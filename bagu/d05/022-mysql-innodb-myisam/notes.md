# 22. InnoDB vs MyISAM · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **存储引擎选型**。现在 OLTP 默认 **InnoDB**；MyISAM 几乎只出现在历史库、只读统计、或面试对比。

## 2. 核心机制（按维度说）

| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | 有，ACID | 无 |
| 锁 | 行锁 + MVCC | 表锁 |
| 崩溃 | redo 恢复 | 易坏，要 repair |
| 外键 | 支持 | 不支持 |
| 索引 | 聚簇，二级回表 | 堆表，索引存行地址 |
| count(*) | 要扫 | 表上有计数，快 |
| 全文 | 5.6+ 有，不如专门搜索 | 早期全文常用 |

**为什么生产选 InnoDB**

- 并发更新同一表不同行：InnoDB 行锁；MyISAM 整表锁死。
- 宕机：InnoDB 靠 redo；MyISAM 索引/数据可能不一致。

**MyISAM 还可能被提到的场景**

- 只读、很少写、要极快 count 的临时统计表（即便如此，很多团队仍用 InnoDB + 汇总）。

## 3. 生产坑 / 反例

- **新项目还选 MyISAM「更快」**——读多写少的微优势换不来崩溃和表锁。
- **混用引擎做外键/事务**：跨引擎事务不成立。
- **系统表 / 临时表** 偶尔还能看到 MyISAM，别和业务表混淆。

## 4. 60 秒口述

> InnoDB 有事务、行锁、MVCC、崩溃恢复、聚簇索引，是默认引擎。MyISAM 表锁、无事务、崩溃易坏，count(*) 可以很快。  
> OLTP 选 InnoDB。对比时抓住事务、锁粒度、恢复、聚簇 vs 堆表这四条就够。
