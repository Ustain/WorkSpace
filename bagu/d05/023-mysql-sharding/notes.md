# 23. 分库分表策略与痛点 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **单机容量/TPS 不够时的水平拆分**。先垂直拆（按领域拆库），再水平拆（一张表按键切开）。

和「读写分离」比：读写分离解决读；分片解决 **写和数据量**。和「分区表」比：分区还在一个实例里，管不了单机上限。

## 2. 核心机制

**拆分键**

- 按 `user_id` hash / 取模：查询带 user_id 能定位；按时间范围查要扫所有分片。
- 按时间：归档方便，热点在最新分片。
- 按地理位置等：看访问模式。

**路由**

- 应用算分片、中间件（ShardingSphere、Vitess）、或代理。
- 分片数最好预留（2 的幂），扩容要对数据做 **rebalance**，非常痛。

**痛点（面试重点）**

1. **跨分片 JOIN / 事务**：基本放弃，改应用层聚合或冗余。
2. **全局二级索引**：按手机号查用户，手机号不是分片键 → 打全分片或另建索引表。
3. **全局唯一 id、分页、count**：都要特殊方案（题 75、20、21）。
4. **扩容迁移**：双写、校验、切流，窗口期长。
5. **非分片键更新**：可能要先查路由表。

**卡点**

- 分片键选错，等于把痛提前锁死。一旦按 user_id 切，按商品维度统计就要离线数仓。

## 3. 生产坑 / 反例

- **过早分片**：单表千万级、索引和归档还能撑时不要上。
- **用 UUID 当拆分键**：无序、难范围、索引页分裂。
- **分片后仍跨库强一致事务**：分布式事务成本高，优先本地消息表（题 73）。

## 4. 60 秒口述

> 分库分表解决单机数据和写入上限。先垂直按域拆，再按分片键水平拆。键一旦选定，所有高频查询都得带它，否则打全分片。  
> 痛点是跨片 JOIN/事务、二级查询、扩容迁移。能用索引、归档、缓存解决就不要分片。分了就要接受应用层聚合和最终一致。
