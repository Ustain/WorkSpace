# 24. 大表 DDL · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **ALTER 怎么避免锁表太久**。大表直接 `ALTER` 可能拷全表、阻塞写，甚至长时间占 MDL。

InnoDB 支持部分 **INPLACE / INSTANT**（8.0 加列可秒级）；不行就用 **gh-ost / pt-osc** 在线拷表。

## 2. 核心机制

**锁与算法（记直觉）**

- **INSTANT**（8.0）：只改数据字典，如特定加列，几乎不拷表。
- **INPLACE**：在原表重建索引/改列，尽量不拷到临时表，但仍可能排写。
- **COPY**：建新表、拷数据、改名。最慢，占双倍空间。

`ALGORITHM=INSTANT|INPLACE|COPY`，`LOCK=NONE|SHARED|EXCLUSIVE`。不支持会报错，别赌。

**在线工具**

- **pt-online-schema-change**：触发器同步增量。
- **gh-ost**：吃 binlog 同步，不在主库装触发器，对主库更友好。

流程：影子表 → 拷存量 + 追增量 → 切表名。切的时候仍有短暂 MDL。

**卡点**

- DDL 等 MDL：被一个长查询占着 `metadata lock`，ALTER 排队，后续 DML 全堵。先杀长查询。
- 磁盘不够拷表 → DDL 失败，业务已半死。

## 3. 生产坑 / 反例

- **高峰直接 ALTER 大表**：即使 INPLACE 也可能把 IO 打满。
- **加二级索引**：要扫全表建树，IO 和延迟从库都会抖。
- **从库 DDL 延迟**：主库秒过，从库拷表几小时，读写分离读到旧结构/延迟。

## 4. 60 秒口述

> 大表 DDL 先看能不能 INSTANT/INPLACE，不能就 gh-ost 或 pt-osc 影子表+追增量再切。真正危险是 MDL：长查询挡住 ALTER，后面所有语句排队。  
> 要看磁盘、从库延迟、业务低峰。加索引等于扫全表，生产要限速。
