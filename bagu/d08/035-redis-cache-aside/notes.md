# 35. Cache-Aside 与读写路径 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **缓存和 DB 谁当主、怎么更新**。互联网默认 **Cache-Aside（旁路缓存）**：应用自己管缓存，DB 是准。

对比：

- **Read-Through / Write-Through**：缓存组件代写 DB，应用简单，组件要成熟。
- **Write-Behind**：先写缓存再异步落库，吞吐高，丢数据风险高。

## 2. 核心机制

**读**

1. 查缓存，命中返回。
2. 未命中：查 DB，回填缓存，返回。

**写（推荐：先 DB 后删缓存）**

1. 更新 DB。
2. **删除** 缓存，而不是更新缓存。
3. 下次读 miss 再回填，避免并发写把旧值写回缓存。

为什么不「先改缓存再改 DB」：DB 失败会脏缓存。  
为什么不「更新缓存」：两个写并发，缓存可能留下更旧的值。

**卡点**

- 先 DB 后删仍有窗口：A 读 miss、B 更新并删缓存、A 把旧 DB 值写回。延迟双删、版本号缓解，不能数学上消掉（题 38）。
- 删失败要重试或发消息补偿。

## 3. 生产坑 / 反例

- **先更新缓存再写 DB**：DB 失败或主从延迟，缓存成谎言。
- **写后更新缓存而不是删**：并发更容易脏。
- **缓存当主存储**：重启或淘汰就丢业务状态。

## 4. 60 秒口述

> Cache-Aside 是应用先读缓存，miss 再读库回填；写是先更新 DB 再删缓存，让下次读自动回填。DB 是准，缓存是加速。  
> 不要先写缓存，也不要在写路径上 set 新值。删失败要补偿。这个模型和延迟双删、穿透击穿是一套组合拳。
