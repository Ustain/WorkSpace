# 38. 延迟双删为什么不严谨 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **Cache-Aside 写后仍可能脏缓存** 的补丁。延迟双删：**删缓存 → 更新 DB → 睡一会儿再删一次**。

它能 **降低** 并发回填旧值的概率，**不能** 在分布式下证明一致。

## 2. 核心机制

**脏窗口（先 DB 后删仍可能）**

1. 读请求 A miss，读到 DB 旧值（还没写回缓存）。
2. 写请求 B 更新 DB 并删除缓存。
3. A 把旧值 SET 进缓存。
4. 缓存变脏，直到过期。

**延迟双删**

- 写完后再删一次，希望赶上 A 的回填。
- 睡眠时间要 > 一次读回填的耗时。经验值，不是上界。

**为什么不严谨**

- 读从库延迟更大，A 可能更晚才写回。
- 机器 STW、GC、网络重试，睡眠不够。
- 第二次删除失败呢？还要重试队列。
- 多级缓存（本地 + Redis）更管不到。

**更稳的方向**

- 缓存短 TTL，接受短暂脏。
- 订阅 binlog 删缓存（canal），以 DB 提交为准。
- 回填带版本号/cas，旧版本写不进去。
- 对强一致读走 DB 或分布式锁串行化该 key。

## 3. 生产坑 / 反例

- **面试把延迟双删当最终方案**——要主动说窗口还在。
- **sleep 放在请求线程里**：拉高 RT，应异步删。
- **只双删 Redis，CDN/本地缓存还脏**。

## 4. 60 秒口述

> 延迟双删是写库后再删一次缓存，减少并发读把旧值写回的概率。它不严谨：睡眠长度拍脑袋，从库延迟和失败重试都会漏。  
> 生产当补偿可以，不能当证明。更稳是短 TTL、binlog 删缓存、或回填带版本。Cache-Aside 默认就是最终一致。
