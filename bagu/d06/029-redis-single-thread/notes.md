# 29. 单线程为什么快，6.0 多线程做什么 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **Redis 线程模型**。口试第一句先限定：**命令执行在主线程串行**，不是整个进程只有一条线程。

6.0+ 多的是 **I/O 线程**（读 socket、解析、写回包），以及一直就有的 **bio 线程**（关 fd、刷 AOF）。**不是把 SET/GET 并行执行**。

## 2. 核心机制

**为什么单线程执行还快**

1. 纯内存，操作大多 O(1)/O(log n)。
2. **I/O 多路复用**（epoll）：一个线程盯成千上万连接，就绪才读。
3. 无锁：执行路径不用为共享可变状态加锁。
4. 高效结构：SDS、跳表、哈希。

**主线程在干什么**

`epoll_wait` → 读请求 → 执行命令 → 写回复。一次只跑一条命令，所以 **单个慢命令会卡住所有人**（大 key、KEYS、FLUSHALL）。

**6.0 I/O 线程**

- 读客户端数据和写响应可以多线程。
- 命令执行仍在主线程。
- 默认不一定开满；配置 `io-threads`。

**卡点**

- 把 Redis 说成「绝对单线程」是错答。
- 多线程 I/O 救不了 `hgetall` 一百万 field。

## 3. 生产坑 / 反例

- **用 KEYS、复杂 Lua、大 key**：主线程堵死，P99 爆炸。
- **把 6.0 多线程理解成并行写同一个 key**：不会，执行仍串行，无竞态。
- **fork 子进程做 RDB**：不是执行多线程，但是会和主进程争内存页（写时复制）。

## 4. 60 秒口述

> Redis 快是因为内存加 epoll，命令在主线程串行执行，没有锁竞争。6.0 多线程只做网络读写，不并行执行命令。  
> 所以单条慢命令会拖垮整个实例。优化方向是拆大 key、禁 KEYS、把重活放到外面，而不是指望多线程执行 SET。
