# 30. 各结构典型业务场景 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **选型题**：先说数据访问模式，再选结构。不要所有东西都用 string 拼 JSON。

## 2. 核心机制（场景对照）

| 类型 | 典型场景 | 不要用来 |
|------|----------|----------|
| **string** | 缓存对象、计数器 INCR、分布式锁、Session | 超大 JSON 当万能袋还不拆 |
| **hash** | 对象字段局部更新（用户资料） | field 几十万的「假表」 |
| **list** | 时间线、简单队列 LPUSH/RPOP | 要 ack、要积压管理（改用 MQ/Stream） |
| **set** | 去重、标签、共同好友 SINTER | 无序且超大集合当列表扫 |
| **zset** | 排行榜、延时任务（score=时间） | 全量用户一个榜 |
| **bitmap** | 签到、布隆之前的存在位 | 稀疏且 key 很多时浪费 |
| **hyperloglog** | UV 近似 | 要精确去重 |
| **geo** | 附近的人 | 复杂地理计算（专业 GIS） |
| **stream** | 可消费组的消息流 | 替代 Kafka 做超大吞吐日志 |

**选型一句话**

- 整存整取 → string。
- 改一个字段 → hash。
- 要顺序 → list/zset。
- 要唯一成员 → set。
- 要分数排名 → zset。

## 3. 生产坑 / 反例

- **list 当核心订单队列**：没消费组、没持久化保障，进程一挂消息处理语义不清。
- **hash 每个 field 一个商品**：商品上亿，一个 key 打爆。
- **用 KEYS 匹配业务前缀当「查询」**：应用层要自己维护索引集合。

## 4. 60 秒口述

> string 做缓存和计数；hash 做对象局部更新；list 做简单时间线；set 做去重和关系；zset 做排行和按时间取。  
> 访问模式决定结构：整存整取用 string，改字段用 hash，要排名用 zset。队列要可靠就 Stream 或 Kafka，不要只用 list。
