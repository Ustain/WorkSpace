# 63. 分片、副本与路由 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **ES 数据怎么铺开**。

- **主分片 primary**：数据切分，**创建索引时就要定好**，后期不能无痛改数量（要 reindex）。
- **副本 replica**：拷贝，提高读和可用性。可随时改个数。

文档路由：`hash(routing) % 主分片数`，默认 routing 是 `_id`。

## 2. 核心机制

- 查询：需要扫 **所有主分片**（除非指定 routing），再在协调节点聚合。
- 分片过多：每个分片有成本（heap、文件），小索引不要 50 个分片。
- 分片过少：单分片太大，恢复慢、无法并行。

经验：单分片 10～50GB 量级（看版本和场景），先少分片，不够再拆索引（按时间）。

**卡点**

- 主分片数 = 并行写入上限之一。
- 副本=0，节点挂就丢那份主分片。

## 3. 生产坑 / 反例

- **一个索引 1000 个分片「为了未来」** → 集群被分片数拖死。
- **不按日期滚动索引**：单索引无限长，分片巨大。
- **自定义 routing 热分片**：某个用户数据极大，打到同一分片。

## 4. 60 秒口述

> 主分片决定数据怎么切，创建时定死；副本提高读和容灾，可改。文档按 routing 哈希进分片。  
> 查询默认打所有分片。分片不是越多越好，小索引少分片，大的按时间拆索引。副本至少 1 才能扛丢节点。
