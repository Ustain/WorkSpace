# 33. 过期策略：惰性 + 定期 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **TTL 到了 key 什么时候删**。Redis 不是到点立刻精确删每一个 key。

两套一起：

- **惰性**：访问时发现过期就删。
- **定期**：后台抽样删除一部分过期 key。

内存满了还有 **淘汰策略**（题 34），和过期不是同一件事。

## 2. 核心机制

**惰性**

- GET 等命令先看 expire，过了就删并返回空。
- 没人访问的过期 key 会继续占内存，直到定期任务或淘汰。

**定期**

- 事件循环里抽一段时间，从过期字典随机抽样，过期就删。
- 若过期比例高，会多循环几轮，但有时间上限，避免堵主线程。

**从库**

- 过期由主库删，从库靠复制过来的 del；读从库时行为要知道版本差异，口试说「过期以主库为准传播」。

**卡点**

- 大量 key 同一时刻过期（整点活动）→ 定期删除来不及 + 雪崩（题 36）。
- `EXISTS` / 写命令也会触发惰性删除。

## 3. 生产坑 / 反例

- **用 TTL 当准时任务**：过期不是闹钟，延迟秒级都可能。准时用 zset 延时或 MQ。
- **过期时间都设成同一秒**：结合缓存雪崩。
- **以为 EXPIRE 后内存立刻下降**：没人碰的 key 还在。

## 4. 60 秒口述

> Redis 过期是惰性加定期：访问时发现过期就删；后台抽样删一批。不是每个 key 到点立刻消失，所以过期 key 可能短暂仍占内存。  
> 大量 key 同时过期会打满 CPU 还可能雪崩，TTL 要加随机。别把过期当精确定时器。
