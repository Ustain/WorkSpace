# 32. AOF rewrite 会不会阻塞 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **AOF 文件膨胀后怎么压缩**。rewrite 不是把旧 AOF 立刻重写，而是 **根据当前内存生成一份更短的 AOF**。

问题核心：会不会堵主线程？答案：**fork 瞬间和少量同步会扰主线程，重写本身在子进程，不阻塞命令执行**；但有缓冲区回写和后期 replace 的短临界区。

## 2. 核心机制

1. 触发：文件太大、`BGREWRITEAOF`、或 rewrite 比例配置。
2. 主进程 **fork** 子进程（这里会抖）。
3. 子进程读自己那份内存快照，写出新 AOF（不阻塞父进程执行命令）。
4. 父进程在 rewrite 期间的新写进 **AOF rewrite 缓冲**。
5. 子进程结束，父进程把缓冲 **追加** 到新文件，然后改名替换旧 AOF。

**会阻塞的点**

- fork：大实例 + 脏页多，停顿和内存峰值。
- rewrite 结束追加缓冲：缓冲极大时，主线程要写一截。
- 磁盘 IO 争用：间接让 RT 变差，不是逻辑锁死。

**不会**

- 子进程遍历生成新 AOF 的那一段长时间循环，不在主线程。

## 3. 生产坑 / 反例

- **高峰 rewrite**：和 RDB 一样，避开流量高峰，或用副本做持久化。
- **rewrite 缓冲爆**：写入极快时，结束阶段主线程卡住更明显。
- **以为 rewrite 会丢掉未 fsync 数据**：正常流程是新旧衔接，不是随便截断。

## 4. 60 秒口述

> AOF rewrite 由子进程根据当前数据生成新文件，命令执行基本不堵。会扰主线程的是 fork，以及结束时把 rewrite 期间的增量刷进新文件。  
> 大实例要在低峰 rewrite，或让从库做持久化。不能说「完全不阻塞」，也不能说「rewrite 全程卡住 Redis」。
