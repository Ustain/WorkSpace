# 74. CAP/BASE：中间件怎么选 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **分区时要一致性还是可用性**。CAP 不是三角全要：网络分区发生时，**CP 或 AP 二选一**。BASE 是工程上的最终一致。

## 2. 核心机制

- **C**：线性/强一致，读到最新提交。
- **A**：每个非故障节点都能响应。
- **P**：分区一定会出现，现代分布式都要认 P。

**中间件直觉**

| 组件 | 更像 | 为什么 |
|------|------|--------|
| ZK / etcd | CP | 过半才写，分区可能不可用 |
| Redis Cluster | AP 偏 | 槽迁、异步复制，切主可丢写 |
| Kafka ISR | 可调 | min.isr+acks=all 偏稳，副本不够就拒绝写 |
| MySQL 异步复制 | AP 味道 | 主可写，从落后 |
| Eureka 类注册 | AP | 宁可脏数据也要找到服务 |
| Consul 等 | 常 CP | Raft |

**BASE**

- Basically Available、Soft state、Eventually consistent。
- 缓存、消息、Saga 都走这条：先可用，再对账修。

**卡点**

- 「我们系统 CAP 全满足」是错答。
- 同一系统不同接口可以不同：付款 CP，feed AP。

## 3. 生产坑 / 反例

- **缓存当 CP**：Redis 锁当账务互斥。
- **把 BASE 当不用对账**：最终一致也要核对。

## 4. 60 秒口述

> 分区时只能保 C 或 A。协调服务 ZK/etcd 选 CP；缓存和很多注册中心偏 AP；Kafka 用 acks 和 min.isr 在丢数据与拒绝写之间调。  
> 业务上资金用强一致存储，展示用最终一致。不要说三角全能要。
