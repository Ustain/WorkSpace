# 72. 接口 / 消息幂等怎么做 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **至少一次投递下，业务只生效一次**。网络重试、MQ 重复、用户双击都会来。

幂等不是 Kafka EOS，也不是数据库事务本身。是 **同一业务键第二次来当第一次成功**。

## 2. 核心机制

**接口**

- 客户端生成 **幂等键**（UUID / 订单号），放头或体。
- 服务端唯一索引或 Redis `SET NX` 记下「这个键已处理」，返回第一次结果。
- 要防的是：处理成功但响应丢失，客户端重试。

**消息**

- 消息里带业务唯一 id。
- 消费表 `uk(biz_id)`：插入成功才做业务；冲突则跳过或查已有结果。
- 先写幂等表再做事，或同一本地事务（消息表方案，题 73）。

**分层**

- 自然幂等：`SET balance=100` 比 `INCR` 更易幂等。
- 去重表 / 唯一约束。
- 状态机：已支付的订单再付一次直接返回成功。

**卡点**

- 只在 Redis 去重：Redis 丢了会重复落库。关键资金用 DB 唯一约束。
- 幂等键范围：按用户？按订单？按请求？要定义碰撞语义。

## 3. 生产坑 / 反例

- **用随机主键当幂等**：每次重试都是新键。
- **先办事后写去重表**：办事成功、写表失败会重复。
- **幂等键不过期无限涨**：要按业务保留策略。

## 4. 60 秒口述

> 幂等是同一业务请求做多次结果一样。接口带幂等键，消息用业务 id 加唯一约束或状态机。关键路径用数据库唯一索引，不要只靠 Redis。  
> 重试是常态，设计接口时就把键定好。EOS 管不到你的订单表。
