# 73. 本地消息表 vs 事务消息 vs Saga · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **跨服务不能用一个 InnoDB 事务时怎么尽量达成**。没有免费的分布式 ACID。

| 方案 | 直觉 | 代价 |
|------|------|------|
| 本地消息表 | 业务和「待发消息」同一本地事务，再异步投递 | 最稳，要扫表 |
| 事务消息（RocketMQ） | 半消息 + 回查 | 依赖 MQ 能力 |
| Saga | 一串本地事务 + 补偿 | 最终一致，补偿难 |
| 2PC/XA | 同步强一致 | 慢、协调者故障痛 |

## 2. 核心机制

**本地消息表（优先会讲）**

1. 更新订单 + 插入 `outbox` 同行事务提交。
2. 定时任务或 CDC 把 outbox 发给 MQ。
3. 下游幂等消费。
只要本地库在，消息不会「业务成了消息没发」。

**事务消息**

- 先发半消息，本地事务成功再 commit；失败回滚半消息。
- Broker 回查本地状态，防进程在 commit 消息前挂。

**Saga**

- 下单、扣库存、扣款各是本地事务。
- 某步失败执行补偿（加回库存）。补偿要幂等，也有失败。

**卡点**

- TCC 更细（Try-Confirm-Cancel），空回滚、悬挂要处理，复杂度高。
- 不要一上来 XA。

## 3. 生产坑 / 反例

- **先发 MQ 再写库**：库失败消息已出，下游假成功。
- **Saga 补偿人工改数据没走状态机**：越补越乱。
- **本地消息表不扫失败重试** → 消息卡住。

## 4. 60 秒口述

> 跨库不要幻想一个事务。最稳是本地消息表：业务和 outbox 同事务，再异步投递，下游幂等。RocketMQ 事务消息是半消息加回查。多步业务流程用 Saga 加补偿。  
> 要强一致才考虑 XA，一般不值得。绝对别先发消息再写库。
