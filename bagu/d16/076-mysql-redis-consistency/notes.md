# 76. 缓存与 DB 一致性方案对比 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **Cache-Aside 之上怎么选一致强度**。默认 **DB 为准、缓存最终一致**。

## 2. 核心机制（从弱到强）

1. **先 DB 后删缓存** + 短 TTL：最常用，有短脏窗。
2. **延迟双删 / 重试队列删缓存**：降低并发回填旧值，不严谨（题 38）。
3. **订阅 binlog 删/更新缓存**：以提交为准，应用漏删也能补。
4. **读走锁 / 读强制 DB**：强一致读，缓存收益下降。
5. **缓存当主（write-behind）**：吞吐高，DB 可丢，一般不用在资金。

**读己之写**

- 写后读主库；或会话里暂时禁用缓存；或版本号。

**卡点**

- 多级缓存（本地+Redis+CDN）要逐级失效，最难。
- 从库延迟 + 回填从库 = 脏得更久。回填应读主或带版本。

## 3. 生产坑 / 反例

- **追求和 DB 实时强一致还用缓存**：很多场景该不缓存或只缓存不可变数据。
- **更新缓存而不是删**：并发脏写。
- **binlog 延迟当实时**：仍有窗口，只是应用层少 bug。

## 4. 60 秒口述

> 默认 Cache-Aside：先写库再删缓存，短 TTL，接受窗口。要更稳用 binlog 删缓存和回填带版本。强一致读就读库。  
> 延迟双删只是补丁。缓存和 DB 不要假装事务。从库回填最容易脏。
