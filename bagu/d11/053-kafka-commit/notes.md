# 53. 自动/手动提交与重复丢失 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **offset 提交时机**。这是消费端丢消息和重复的最常见原因。

## 2. 核心机制

**自动提交** `enable.auto.commit=true`

- 隔一段时间提交 poll 到的最大 offset。
- **先提交后处理失败** → 丢。
- 处理完还没到点提交就挂 → 重复。
- 省事但不安全，生产业务消费不建议。

**手动提交**

- 处理成功后再 `commitSync/commitAsync`。
- 默认 **至少一次**：失败重试会重复，靠业务幂等。
- 想减少重复：处理+提交做成更细粒度，或事务消费（仍要业务幂等）。

**两种手动**

- 同步提交：失败能感知，会挡消费。
- 异步提交：吞吐高，失败要回调补。

**卡点**

- 批量处理 100 条，第 50 条失败：offset 怎么交决定丢还是重复。
- 提交比 HW 还超前：不会；但提交自己没处理完的 offset 会丢。

## 3. 生产坑 / 反例

- **自动提交 + 长耗时处理** → 典型丢失。
- **每条都 commitSync**：吞吐差，rebalance 更敏感。
- **异步提交失败当成功**：位点跳跃。

## 4. 60 秒口述

> 自动提交可能先交位点再处理，失败就丢；没交上就挂则重复。业务消费用手处理成功再提交，接受至少一次，用幂等去重。  
> 批量失败要有策略：整批重试或落到失败队列，别稀里糊涂往前交 offset。
