# 52. Rebalance 原因与减少抖动 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **消费组重新分配分区**。rebalance 期间该组往往 **暂停消费**，表现为延迟、重复、心跳超时连锁。

## 2. 核心机制

**谁触发**

- 消费者加入/离开/崩溃（心跳超时 `session.timeout`）。
- 订阅的 Topic 分区数变化。
- 订阅关系变化。

**协议演进**

- 早期 **Stop the World** 全组停。
- **协同再均衡 Cooperative Sticky**（2.4+）：尽量只动受影响分区，减少停顿。
- 静态成员 `group.instance.id`：重启短时间内不踢出，避免发布就 rebalance。

**卡点**

- 处理消息太久不 poll：被当死掉踢出 → rebalance → 重复分配。
- `max.poll.interval` 和真实处理时间不匹配。

## 3. 生产坑 / 反例

- **消费里做重 RPC**：poll 间隔爆掉，反复 rebalance。应先拉取、快速提交进度策略要谨慎，重活用线程池但保序。
- **频繁发版**：用静态成员或滚动时先停消费再启。
- **session.timeout 太小**：网络抖就踢人。

## 4. 60 秒口述

> 组成员变化或分区变化就会 rebalance，期间消费停顿还可能重复。减少抖动：协同再均衡、静态成员、处理时间别超过 max.poll.interval、心跳参数别过紧。  
> 根因经常是业务处理太慢被踢组，不是 Broker 坏了。
