# 50. 分区策略与顺序保证 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **消息进哪个分区、顺序能保证到哪一层**。Kafka **只保证分区内顺序**，不保证 Topic 全局顺序。

## 2. 核心机制

**默认分区**

- 有 key：`hash(key) % 分区数` → 同 key 同分区 → **同 key 有序**。
- 无 key：sticky / round-robin，打散吞吐，**无序**。
- 也可自定义分区器。

**顺序要成立还要**

1. 生产端：同 key、幂等、限制 in-flight，避免重试插队。
2. Broker：分区日志追加顺序。
3. 消费端：**单线程处理该分区**（或处理完再拉下一批），组内一分区分给一个消费者。

**全局顺序**

- 只能 **单分区**。吞吐变成一台消费者。一般不这么干。
- 业务上把「要有序的那部分」做成同一个 key（订单 id）。

**扩分区副作用**

- 分区数变了，hash 取模变了，**同 key 可能换分区**，历史顺序断裂。扩容要接受或不用 hash 依赖。

## 3. 生产坑 / 反例

- **「Kafka 有序」不说范围**——必须说分区内 / 同 key。
- **消费并行线程抢同一分区消息**——把顺序打乱。
- **先扩分区再指望老 key 还在原分区**。

## 4. 60 秒口述

> 顺序只在分区内。同 key 哈希到同一分区就能保该 key 的顺序，还要求生产不乱序重试、消费单线程处理该分区。全局有序等于单分区。  
> 扩分区会改变 hash 映射。面试别说 Kafka 全局有序。
