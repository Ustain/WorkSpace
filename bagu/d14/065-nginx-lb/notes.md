# 65. 负载均衡算法 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **upstream 怎么挑机器**。Nginx 开源常见：轮询、加权、ip_hash、least_conn；一致性哈希、更智能的算法在 Plus 或 OpenResty。

## 2. 核心机制

| 算法 | 行为 | 适用 |
|------|------|------|
| round-robin | 轮询 | 机器差不多 |
| weight | 加权轮询 | 机器规格不同 |
| ip_hash | 同客户端 IP 进同一台 | 要会话粘滞（有一致性风险） |
| least_conn | 连得少的优先 | 长连接、耗时不均 |
| hash key | 按 uri/key 哈希 | 缓存命中、粘滞 |

**会话**

- ip_hash 在节点增减时会打乱。
- 更好是 **应用无状态 + 共享 Session（Redis）**，负载算法随便轮询。

**卡点**

- 加权只影响新请求比例，救不了一台已经打满的慢节点（要健康检查）。
- ip_hash 遇 NAT 出口，大量用户同一 IP，变成单点。

## 3. 生产坑 / 反例

- **有状态服务靠 ip_hash 撑**：扩容就丢会话。
- **least_conn 但健康检查没开**：连着的是 hang 住的连接。

## 4. 60 秒口述

> 默认轮询，机器不均用加权，长连接用 least_conn，要粘滞用 ip_hash 或 hash。最好应用无状态，会话放 Redis，负载算法保持简单。  
> NAT 下 ip_hash 会倾斜。节点摘除要配合 max_fails。
