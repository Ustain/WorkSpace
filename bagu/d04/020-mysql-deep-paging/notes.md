# 20. 深分页优化 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **`LIMIT 1000000, 20` 为什么越往后越慢**。不是「LIMIT 语法」，是扫描丢弃太多行。

InnoDB 执行 `OFFSET 1000000`：先沿着索引读 1000020 行（可能还回表），丢掉前 100 万，只留 20。越深越慢。

## 2. 核心机制与改法

**延迟关联（最常用）**

```sql
-- 坏：回表 1000020 次量级
SELECT * FROM t ORDER BY id LIMIT 1000000, 20;

-- 好：子查询只扫主键，再回 20 行
SELECT t.* FROM t
JOIN (
  SELECT id FROM t ORDER BY id LIMIT 1000000, 20
) x ON t.id = x.id;
```

覆盖索引扫叶子拿 id，最后才回表 20 次。

**seek / 游标分页（推荐产品形态）**

```sql
SELECT * FROM t WHERE id > :last_id ORDER BY id LIMIT 20;
```

记住上一页最后一条主键（或 `(sort_key, id)`），直接定位，**复杂度与页码无关**。

**业务改法**

- 禁止跳到第 1 万页；搜索用 ES；导出走异步任务。
- `ORDER BY` 无索引时深分页会 filesort + 临时表，更惨。

**卡点**

- 游标分页遇到删除/插入会跳行或重复，需要稳定排序键（唯一）。
- 非主键排序：延迟关联要用「排序列 + 主键」覆盖索引。

## 3. 生产坑 / 反例

- **前端无限页码**：必须改成下拉加载 + last_id。
- **只加 LIMIT 不改 OFFSET**：第 N 页依然 O(N)。
- **从库深分页**：还叠加延迟和更差缓存，更易超时。

## 4. 60 秒口述

> OFFSET 深分页要先扫掉前面所有行再丢弃，越深越慢。优化两招：延迟关联，子查询只走覆盖索引取主键再回表；更好的是 where id > last_id 的游标分页，成本与页码无关。  
> 产品上别让用户跳一万页。排序列必须有索引，否则 filesort 比 OFFSET 还可怕。
