# 17. 主从延迟原因与治理 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **从库追不上主库**。指标常看 `Seconds_Behind_Master` / `SHOW REPLICA STATUS` 的 `Retrieved/Executed_Gtid_Set` 差，或监控秒级延迟。

和「主库慢」不同：主库 TPS 正常，从库 apply 慢，读写分离读到旧数据。

## 2. 核心机制，卡在哪会出问题？

**延迟从哪来（按链路说）**

1. **主库 dump 慢**：binlog 刷盘、dump 单线程、网络带宽。
2. **I/O 线程慢**：网络、从库盘写 relay。
3. **SQL/worker 慢**（最常见）：
   - 从库配置比主库差（磁盘、缓冲池）。
   - **大事务 / DDL** 串行堵住并行队列。
   - 从库有额外索引或不同参数，重放更贵。
   - 表无主键，ROW 更新要扫全表。
   - 从库上跑分析 SQL，抢 IO。

**卡点**

- `Seconds_Behind_Master` 在并行复制下不精确，可能跳变。用 GTID 差或心跳表更准。
- 延迟 0 不代表「刚写入立刻可读」，半同步也只保证收到日志。

## 3. 生产坑 / 反例

- **读写分离不处理延迟**：用户刚下单，列表从库还没有。方案：强制读主、会话一致性（读自己的写）、延迟阈值摘从库。
- **无主键大表**：ROW 更新从库全表扫，延迟爆炸。
- **只扩从库数量**：每个从库都要重放全量 binlog，不减 apply 压力；要升配、并行、拆库。

## 4. 60 秒口述

> 主从延迟多半是从库 SQL 重放慢：大事务、DDL、无主键、从库更弱或被分析查询抢资源。网络和 dump 也会拖，但生产最常见是 apply。  
> 治理：主库拆小事务、表有主键、从库配齐、并行复制、监控 GTID 差。读写分离要有读主通道或延迟熔断，不能假设从库实时。
