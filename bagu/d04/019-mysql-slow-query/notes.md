# 19. 慢查询优化路径 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **线上 SQL 变慢怎么从现象走到改动**。固定顺序，别一上来分库分表。

路径：**确认慢 → Explain → 改 SQL/索引 → 改表结构 → 最后才架构**。

## 2. 核心机制（面试按步骤说）

**① 找到真凶**

- `slow_query_log` + `long_query_time`；或 performance_schema / pt-query-digest。
- 看是偶发还是稳定慢；是某一条 SQL 还是整实例 IO 打满。

**② Explain / EXPLAIN ANALYZE**

- 有没有索引、是否回表、rows 是否离谱、有没有 filesort/临时表。

**③ 优先低成本改法**

1. **改 SQL**：去掉函数包列、隐式转换、`SELECT *`、深分页、相关子查询改 JOIN。
2. **加/改索引**：联合索引覆盖 WHERE+ORDER BY；覆盖索引避免回表。
3. **改数据访问**：批量代替循环查；避免 N+1。
4. **表与统计**：`ANALYZE TABLE`；过长 varchar、错误类型。
5. **实例层**：缓冲池、临时表落盘、锁等待（可能不是 SQL 本身慢）。

**④ 仍不够**

- 读写分离、缓存、归档冷数据、分库分表（题 23）。

**卡点**

- 慢在等锁，Explain 看起来很好 → 查 `SHOW ENGINE INNODB STATUS`、锁等待。
- 慢在单行回表十万次 → 覆盖索引比再加机器有效。

## 3. 生产坑 / 反例

- **一慢就加索引**：写放大、优化器选错；先证明是扫描/回表问题。
- **一慢就分表**：迁移成本最高，应是最后一步。
- **只优化平均、忽略尾延迟**：大页、冷缓存、一次没走索引的执行也会告警。

## 4. 60 秒口述

> 慢查询先捞慢日志定位 SQL，再 Explain 看 type、key、rows、Extra。优先改写法让列裸奔、补联合/覆盖索引、消 N+1，统计信息不准就 ANALYZE。锁等待和 IO 打满要当另一类问题。分库分表是最后手段。
