# 16. 主从复制流程与并行复制 · 口试

## 1. 属于哪块？和相邻方案差在哪？

属于 **binlog 怎么从主库到从库**。不是 redo 同步，也不是共享存储双活。

经典三线程：

1. 主库 **dump 线程**：读 binlog，推给从库。
2. 从库 **I/O 线程**：写成 **relay log**。
3. 从库 **SQL 线程**：重放 relay，改从库数据。

并行复制是把「一个 SQL 线程」变成 **多个 worker**，降低延迟。

## 2. 核心机制，卡在哪会出问题？

**复制模式**

- **异步**（默认）：主库提交完就返回，从库稍后追。主挂可能丢未传来的 binlog。
- **半同步**：至少一台从库收到 binlog（写到 relay）才给客户端成功。还没重放完。
- **组复制 / MGR**：多数派，更接近防丢，运维更重。

**位点**

- 传统：`File + Position`。
- GTID：每个事务全局 id，failover 更不容易错位点。生产优先 GTID。

**并行复制演进（说版本直觉）**

- 5.6：按库并行（`DATABASE`），同库还是串行。
- 5.7：基于组提交的 **LOGICAL_CLOCK**，同一 commit 组可并行。
- 8.0：写集合检测更细，冲突少的事务并行度更高。

**卡点**

- 从库只保证「最终跟上」，不保证读到最新（读写分离要处理延迟，题 17）。
- ROW 格式重放按行改，安全；STATEMENT 可能主从不一致。

## 3. 生产坑 / 反例

- **主库大事务**：一个事务 binlog 巨大，从库 SQL 线程卡很久，并行也救不了「单个大事务」。
- **从库只开了 I/O 没追上 SQL**：`Seconds_Behind_Master` 看起来怪，要看 relay 是否堆积。
- **主从并行 DDL**：从库 DDL 和 DML 互相堵，延迟尖刺。

## 4. 60 秒口述

> 主库 dump 把 binlog 给从库 I/O 线程写成 relay，SQL 线程（或并行 worker）重放。复制的是 binlog 不是 redo。  
> 异步快可能丢；半同步至少等到从库落 relay。并行复制按库或按 commit 组多 worker 重放，但单个大事务仍然是延迟杀手。生产用 GTID + ROW。
