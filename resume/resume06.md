## 项目经历

### 1. 支付渠道回调网关 | 核心开发 2026.02 – 2026.05

**技术栈：** Go / Redis / MySQL / Kafka

**项目介绍：** 面向微信、支付宝等多支付渠道的回调统一接入与异步分发系统。通过统一网关完成协议适配与验签解密，并以消息队列驱动下游异步履约，将渠道超时与业务处理解耦。
 
**个人职责：**

- 设计并实现多渠道回调接入层，完成明文/密文及 XML/JSON 报文适配、签名校验与 AES 解密，将微信、支付宝等渠道收口为统一通知模型，渠道只需对接网关一层
- 实现 Redis 短窗去重，以渠道加通知号为键做 `SET NX EX` 拦截并发双击；窗口外以 MySQL 唯一约束写入通知流水，用状态机追踪入库、入队与消费确认，保证同一通知可重复投递且进度可查
- 设计 Kafka 异步分发链路，验签落库成功后按通知类型分区投递，消费者至少一次消费并按类型分流到支付、退款或业务回调；投递失败回写流水状态并进入延迟重试
- 实现下游保护策略，按渠道限制并发处理数量，并对出站调用加超时与熔断，避免短时密集重试打垮支付服务，同时保证网关自身仍能响应渠道
- 实现失败补偿与可追踪闭环，结合 Redis 延迟队列做阶梯重试，终态失败落库待人工或定时补偿，ACK 成功后将流水置为完成

**项目亮点：**

- 针对多渠道协议不统一、业务重复对接，将验签、解密与报文适配收敛到统一网关，一套主流程兼容明文/密文、XML/JSON，新增渠道只需扩展适配而不改分发主链路
- 针对渠道重试带来的重复入账风险，Redis 短窗挡并发、MySQL 唯一键做权威去重，状态机区分已受理与已完成，重复消费由下游幂等兜底
- 针对下游处理慢导致渠道超时重推，落库后写入 Kafka 再异步消费，入队成功即可对渠道成功应答，把渠道时限与履约耗时拆开
- 针对密集重试压垮下游，按渠道做并发限流，出站超时并熔断，失败消息进 Redis 延迟重试而非堵在热路径，网关入口保持可响应

### 2. 支付 AI 智能客服系统 | 核心开发 2026.06 – 2026.08

**技术栈：** Python / FastAPI / LangGraph  / RAG / Milvus

**项目介绍：** 基于 Python、FastAPI、LangGraph 和通义千问构建的 API 开放平台多 Agent 智能客服系统。以 LangGraph DAG 编排为核心，集成意图路由、RAG 混合检索、工具诊断、会话记忆、安全脱敏和多级兜底，为开发者提供端到端技术支持。

**个人职责：**

- 设计并实现多 Agent 协作架构，基于 LangGraph StateGraph 将意图路由、文档 RAG、API 诊断、账单、工单和安全审查六个专业 Agent 编排为固定 DAG，由中心编排器统一管理状态流转与并行执行
- 实现 RAG 混合检索系统，采用 text-embedding-v3 生成 1024 维向量，与 BM25 双路并行召回，经 RRF 融合、gte-rerank-v2 精排和上下文压缩后带引用生成
- 设计两级容错机制，隔离单个 Agent 异常，整条管线发生不可恢复异常时自动降级为规则回复并创建人工工单
- 实现覆盖 API Key、Token、手机号等八类敏感信息的输入、工具日志和最终输出三层脱敏，并将安全审查置于管线末端，确保所有回复经过安全检查
- 实现语义缓存、路由缓存和模型分层，简单任务使用小模型、复杂任务使用大模型；通过逐节点链路追踪实现全链路可观测与按租户成本统计

**项目亮点：**

- 针对单 LLM 在长链路诊断中易走偏、难并行和故障难隔离的问题，引入多 Agent 编排并结合缓存、模型分层和并行执行，将冷请求 P95 从 48.58s 降至 6.83s，吞吐从 0.18 提升至 0.75 req/s
- 设计基于查询向量余弦相似度的语义缓存，热点重复问题命中时 0.38s 返回且零 Token 消耗，相比完整链路加速约 26 倍
- 为错误码类问题设计数据库精确匹配热路径，绕过向量检索和模型生成，处理耗时由 0.74s 降至 0.010s
- 通过向量与 BM25 双路召回、RRF 融合和精排兼顾语义及关键词匹配；在 15 例标准评测集上，意图路由、答案引用和敏感信息脱敏准确率均达到 100%
