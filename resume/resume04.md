## 项目经历

### 1. 支付实时监控系统 | 核心开发 2025.10 – 2025.12

**技术栈：** Go / Redis / Kafka / MySQL / Prometheus

**项目描述：** 为支付系统构建实时风控监控系统，基于滑动窗口与规则表达式，对订单创建、支付完成等事件流做实时特征计算与风险判定，支撑日均百万级订单的实时监控告警。

**职责与成果：**

- 设计基于 Redis 滑动窗口的特征聚合方案（用户维度/商品维度/IP维度），窗口粒度支持 1 分钟~24 小时，单次聚合走 Lua
- 实现规则热加载机制：规则变更经配置下发到各节点本地缓存，秒级生效，避免全量发版
- 告警收敛：命中后推送告警并清理窗口计数，避免同一主体短时间重复命中触发告警噪音
- AI 根因分析：掉单 / 延迟告警异步触发 Agent 根因分析，分析结果 webhook 发送到值班群，触发补单或者客服售后操作
- 可观测性：接入 Prometheus 埋点，按规则维度上报命中率、误报率、处理耗时，配合 Grafana 看板实时监控

### 2. 支付渠道回调网关 | 核心开发 2026.03 – 2026.05

**技术栈：** Go / Redis / Kafka / MySQL

**项目描述：** 支付渠道回调的统一接入层。微信、支付宝等通知先在网关完成验签和解密，经 Redis 去重、MySQL 记流水后写入 Kafka，再异步转发到支付回调或业务服务。

**职责与成果：**

- 负责多渠道回调统一接入，完成明文/密文、XML/JSON 适配与验签，渠道只需对接网关一层
- 基于 Redis 短窗去重和 MySQL 通知流水，保证同一笔通知可重复投递、状态可追踪
- 将下游处理改为 Kafka 异步消费，按通知类型分流到支付回调或业务服务，失败可回写流水并重试
- 按渠道限制并发处理的回调数量，避免三方渠道短时间的密集重试把下游支付服务压垮
- 转发下游加超时和熔断，支付服务变慢时回调网关不会被拖死，渠道入口仍能响应
