## 一、支付实时监控系统 · 八股

### Q1. 滑动窗口怎么实现，24 小时窗口的成本算过没有

简历原句：设计基于 Redis 滑动窗口的特征聚合方案（用户维度/商品维度/IP维度），窗口粒度支持1分钟~24小时。

**问题：** 滑动窗口和固定窗口计数差在哪？你用的是 ZSET 逐事件存，还是分桶近似？一个 NAT 出口 IP 一天几万笔订单，24 小时窗口下这个结构多大、每次判定多贵？

**参考答案：**

固定窗口是 `INCR` 加 `EXPIRE`，两个窗口交界处计数叠加，攻击者专挑边界打。真滑动窗口用 ZSET：成员是事件唯一 ID，score 是毫秒时间戳，判定时 `ZREMRANGEBYSCORE` 清掉窗口外成员再 `ZCARD` 取数，边界平滑。

成本在长窗口高基数维度。按成员 60~100 字节算，一个 IP 一天五万笔订单就是 3~5 MB 的大 key，清理和判定都是对几万成员的操作，热 IP 会吃掉 Redis 单线程的大块时间。用户维度没事，一个用户一天几十笔顶天。

工程通行做法是分桶近似：按 1 分钟一个桶计数，24 小时窗口就是最近 1440 个桶求和，内存只与窗口时长除以桶粒度有关，与事件量无关。风控场景几乎都接受近似滑动。面试要主动说清用的是哪种；答 ZSET 就要接得住大 key 和热点追问：IP 维度按基数上限降级为限频，或对超大成员抽样。

### Q2. 聚合走 Lua，原子性到底保住什么

简历原句：单次聚合走 Lua。

**问题：** 清旧成员、写新事件、读计数三步分开执行会出什么错？脚本执行到一半 Redis 崩了，窗口数据会怎样？脚本执行期间别的请求在干什么？

**参考答案：**

三步分开，两个并发事件交错执行：A 清完旧成员还没写自己，B 也清完写了自己，A 再读数时清理重复做了两次，读到的计数还可能漏掉 B 刚写入的成员。特征计算要求「读到的计数包含本次事件、且清理只做一次」，这个复合动作必须一次提交。Lua 在 Redis 单线程里串行执行完，中间不插入别的命令。

Redis 脚本是原子的但不是事务：中途报错，已执行的写不回滚。所以脚本里的写要放在读取和校验之后，错误分支不能留半截状态。

脚本执行期间整个实例阻塞，所有请求排队。这反过来限制了脚本里的操作量：24 小时 ZSET 清几万成员是 O(M) 的活，热 key 下单次脚本毫秒到十毫秒级，全实例跟着卡。这是 Q1 选分桶方案的第二个理由。脚本用 `EVALSHA` 并处理 NOSCRIPT（重启、主从切换后先 `EVAL` 加载一次）；集群模式下脚本涉及的所有 key 必须在同一 slot，多维度 key 进不了同一段脚本，原子性只在单维度内成立。

### Q3. 三个维度，key 怎么设计，过期怎么定

简历原句：特征聚合方案（用户维度/商品维度/IP维度）。

**问题：** 维度 key 是独立三份，还是做组合（用户+商品）？key 总量什么量级？TTL 设多久，TTL 到期和窗口没滑完撞在一起会怎样？

**参考答案：**

独立维度 key 是基础：`risk:u:{uid}:pay`、`risk:g:{gid}:pay`、`risk:ip:{ip}:pay`。组合维度（用户×商品）是可选增强，key 数是基数乘积，24 小时窗口下要保留的活跃组合量决定内存账，组合维度通常只给高风险场景开。

TTL 必须大于窗口时长再加缓冲：24 小时窗口的 key，TTL 设 25 小时以上，每次写入刷新，活跃 key 常驻、冷 key 自然过期。TTL 短于窗口是正确性 bug：长窗口特征在 key 过期那一刻清零，攻击者把行为拖过 TTL，特征就断档。

高基数维度要控制 key 空间：IPv6、代理池产生的 IP 没有上限，IP 维度通常另做处理（限频，或只对命中过初筛规则的 IP 建特征），否则 Redis 里几十万个只写一次的 key，内存和过期扫描都是负担。面试能报出「预期活跃 key 数量级和总内存估算」这一句，比堆三个维度名词有说服力。

### Q4. 事件重复和乱序，窗口计数会怎样

简历原句：对订单创建、支付完成等事件流做实时特征计算与风险判定。

**问题：** Kafka 至少一次消费，重复事件进窗口，计数会怎样？score 用事件发生时间还是处理时间？支付完成事件先于订单创建事件到达，判定会怎样？

**参考答案：**

至少一次消费意味着重复投递。ZSET 方案里成员用事件唯一 ID（订单号+事件类型），`ZADD` 对同成员是覆盖不是累加，天然幂等，重复消费不会让计数翻倍。分桶 `INCR` 方案不幂等，重复消息会让桶计数虚高、误报上升，必须先做事件去重（`SET NX` 记事件 ID，或消费者按事件 ID 查重）再进桶。面试先讲清你选的方案在重复消息下是什么行为。

score 的选择要讲清语义：用事件发生时间，乱序晚到的旧事件 score 落在窗口深处，`ZCARD` 已经读过的判定不会重算，这一笔就漏掉了；用处理时间，计数不漏但窗口语义向「处理时刻」漂移。风控通常接受「最终正确、实时略偏」：实时判定用处理时间，重算和对账修正离线做。关键是主动说选了哪个、放弃的那一路丢的是什么。

乱序本身不拦截：跨分区的支付完成和订单创建没有顺序保证，单条事件的特征聚合只依赖这一事件自身，不依赖事件间顺序，这个设计选择要能说出口。

### Q5. 规则热加载，版本切换的一致性

简历原句：实现规则热加载机制：规则变更经配置下发到各节点本地缓存，秒级生效，避免全量发版。

**问题：** 一条事件的判定跨新旧两个规则版本，会发生什么？规则集在 goroutine 之间怎么安全替换？新配置加载失败怎么办？

**参考答案：**

规则集编译成不可变对象（表达式先 parse 好，不能每条事件重新 parse），加载新版本后用 `atomic.Value` 整体替换指针，判定方每次 `Load` 拿到完整快照。一条事件从取特征到跑完全部规则，用同一个快照，不能每条规则各取一次，否则一次判定混用两个版本的规则。

配置中心 watch 是最终一致：各节点生效时间不同步，「秒级生效」是大多数节点秒级，不是全集群原子切换。对风控这可接受（规则版本影响检出率，不影响正确性），但要主动说出来。

加载失败保留旧版本并告警，绝不能让规则表变成空的。配置带版本号和校验和，写坏的内容在加载时被挡住。回滚就是下发旧版本，走同一条热加载链路，不回滚代码。

规则是内部人写的也要防：正则规则限制长度和回溯深度，防 ReDoS；表达式引擎限制执行耗时上限，一条坏规则不能拖住整个消费线程。

### Q6. 按规则维度上报命中率，误报率怎么来的

简历原句：接入Prometheus埋点，按规则维度上报命中率、误报率、处理耗时，配合Grafana看板实时监控。

**问题：** 命中率的分子分母各是什么？没有触发的规则，评估数还在不在？误报率是实时指标算出来的吗？规则维度标签的基数上限是多少？

**参考答案：**

命中率 = 规则触发事件数 / 该规则被评估事件数。评估数这个分母必须有：只报触发数，看不见「一条规则什么时候死了」（配置错、特征断了、流量变了），看板上它会静默消失而不是报警。

误报率不是实时指标能算的。实时只能算触发率；「误报」需要人工标注、客诉回溯这类离线反馈才能定义。看板上的误报率要说明数据来自标注流程和更新周期，否则面试官追问「误报标签谁打的」，答案出不来。

标签基数：规则数量可控（几十到几百），按规则 ID 加标签安全；用户、订单、IP 绝对不能进标签，基数会打爆时序库，它们只进日志和 trace。Histogram 的 bucket 也算基数，耗时 bucket 数乘以规则数要控制。

处理耗时要分段：窗口查询耗时、规则评估耗时、事件总耗时三段分开报。混成一段，Redis 抖动和规则变慢看板上看不出来，定位时间就回去了——这正好和简历里「缩短定位时间」的卖点对上。

## 二、支付实时监控系统 · 业务场景

### Q7. 命中告警后清理窗口计数，这个按钮在谁手里

简历原句：告警收敛：命中后推送告警并清理窗口计数，避免同一主体短时间重复命中触发告警噪音。

**问题：** 攻击者发现「触发一次告警计数就清零」，怎么利用？清理的是哪个 key？告警收敛和特征重置是不是一回事？

**参考答案：**

清零等于给攻击者一个免费重置按钮：先用小额高频触发一次告警把计数清掉，紧接着发起真正的攻击，长窗口特征已经归零。风控里「处置动作改变特征状态」是经典漏洞，和「输错密码就重置错误计数」一个性质。

正确做法是把两件事拆开：告警收敛在告警通道做——同主体+同规则在 N 分钟内聚合为一条通知，带累计触发次数和首次时间；特征窗口照常累计，不被告警行为影响。如果确认误报后确要清理（例如 IP 归属识别错误），清理动作走人工或白名单，记审计日志，且清的是「已处置」标记而不是原始计数。

面试被问到这句时，主动改口：「清理」指的是告警侧的去重标记，特征数据不清理。按简历字面意思答「清零计数」，等于承认了一个可被利用的设计。

### Q8. 掉单的定义，实时系统怎么知道渠道扣了款

简历原句：主导支付订单实时监控系统从0到1的开发落地，覆盖掉单、延迟等异常场景的检测，支持自动补单和告警。

**问题：** 什么叫掉单？「渠道已扣款、我方无单」这个事实，实时事件流里存在吗？你是靠什么数据源发现的？

**参考答案：**

掉单至少三类：渠道有我方无（回调丢失或验签失败被丢弃）；两边都有但状态不一致（我方停在待支付、渠道已扣款，即回调没处理成功）；我方有渠道无（用户从未支付，单还开着）。

实时事件流里只有第二类能直接发现：事件流内部有订单创建和支付完成，超时对比可查。第一类「渠道扣了款但我方没收到回调」，事件流里根本没有这个事实——我方不知道渠道发生了什么。发现路径只有两条：主动查单（对超时未支付订单调渠道查单接口，确认渠道侧真实状态），和 T+1 渠道账单对账兜底。

面试要按数据源分层回答：实时检测覆盖「事件流内部矛盾」（延迟、状态不一致）；准实时覆盖「主动查单补齐」（回调丢失）；T+1 对账兜底全部。简历一句「覆盖掉单」背后是三层，讲不出分层就会被追问「你怎么在流里知道渠道扣款了」而卡住。

### Q9. 自动补单的安全边界在哪

简历原句：支持自动补单和告警。

**问题：** 什么单可以自动补？补单调的是什么接口？补单和回调处理并发执行，同一单会不会补出两笔履约？渠道故障恢复后堆积的掉单集中补，会怎样？

**参考答案：**

能自动补的只有一类：查询确认型——先调渠道查单确认已扣款、金额一致，再触发我方「支付成功处理」。金额不一致、需要退款、对账差异，全部人工。绝不能「没收到回调就默认成功」直接履约。

补单不是一条独立链路：它必须复用回调处理的同一个入口、同一套幂等（订单号唯一约束加状态机条件更新）。补单和迟到的回调并发到达，两个都进状态机，只有一个能把「待支付」迁到「已支付」，另一个拿到 0 行影响或键冲突后走读状态分支。另写一条绕过状态机的补单路径，就是双重履约的来源。

补单要限流排队：渠道故障恢复后掉单集中暴露，补单接口按固定速率消化，观察下游水位。补单本身也要可观测——补成多少、失败多少、失败原因分布，否则「自动补单」上线后没人知道它在干什么。

### Q10. AI 根因分析，结论能直接驱动补单吗

简历原句：AI根因分析：掉单 / 延迟告警异步触发 Agent 根因分析，分析结果webhook发送到值班群，触发补单或者客服售后操作。

**问题：** Agent 拿到的上下文是什么？怎么防止它编一个根因？「触发补单」是 Agent 输出直接执行的吗？告警风暴时 Agent 调用量会怎样？

**参考答案：**

上下文是结构化的：告警事件（订单号、规则、时间线）、该订单在监控和网关侧的状态轨迹、渠道查单结果、同时段相关指标（消费延迟、错误率、Redis 延迟）。不是丢一句「帮我看下这个告警」。

防幻觉靠输出约束：根因映射到预定义枚举（回调丢失 / 下游处理失败 / 渠道未扣款 / 渠道接口异常 / 无法定位），每条结论必须附证据引用（流水号、日志行、指标快照）。证据不足就输出「无法定位，转人工」，不允许自由文本结论直接驱动动作。

动作分级：Agent 可以直接触发查询类补单（走 Q9 的安全入口，状态机幂等兜底）；退款、售后补偿这类写操作只能生成待办，值班人确认后执行。webhook 消息里带根因类型、置信度、证据链接，人能三秒内复核。

费用与风暴：每次根因分析是 LLM 调用，告警风暴就是调用风暴。按根因类型聚合后抽样分析、同根因结果去重合并，Agent 侧也设调用预算和熔断——分析服务挂了不能影响告警主链路，它是异步增强，不是必经路径。

### Q11. 日均百万级订单，这套系统的真实压力在哪

简历原句：支撑日均百万级订单的实时监控告警。

**问题：** 日均百万单对应多少事件、多少 Redis 操作？峰值 QPS 算出来是多少？单实例 Redis 够吗？这个量级下系统真正的难点是什么？

**参考答案：**

百万订单 × 每单 2~4 个事件（创建、支付、履约）≈ 200~400 万事件/天，平均 25~50 事件/秒，峰值按 5~10 倍算 250~500/秒。每事件三维度聚合（pipeline 或一次 Lua）约 3 次 Redis 往返，峰值 1500 ops/s 量级——单实例 Redis 十万 ops/s，总量毫无压力。Kafka 在这个量级提供的价值是削峰、重放和隔离，不是吞吐刚需。

所以「日均百万级」不是吞吐卖点，面试官追问「难在哪」时，答案要落在：长窗口大 key 和热点 IP（Q1）、维度 key 的内存账（Q3）、重复乱序的幂等（Q4）、规则热加载的正确性（Q5）、告警风暴与误报治理（Q6/Q7）。能按这个顺序讲难点，百万级这句话才立得住；答「并发高、数据量大」，量级一算就穿。

被问容量规划还要给增长余量：订单涨十倍到千万级，先分维度拆实例（用户维度和 IP 维度分开）、桶粒度随窗口调整、监控消费组和规则引擎水平扩。这套方案在千万级内不需要换架构，说出来是加分项。

### Q12. 「延迟」怎么定义，检测任务靠什么触发

简历原句：覆盖掉单、延迟等异常场景的检测。

**问题：** 订单创建后 10 分钟没支付算延迟吗？扫描任务和事件流各负责什么？延迟检测自己需要一个什么设施？

**参考答案：**

延迟阈值必须按支付方式和场景分：扫码支付秒级、H5 收银台分钟级、银行转账小时级、大额 B2B 更长。单一阈值会把大量正常慢支付打成异常，误报直接淹没值班群——这正是简历里告警收敛要对抗的东西，源头却在阈值设计。

事件流不会帮你等：Kafka 消费到「订单创建」时，用户可能十分钟后才支付，消费者不能挂起等。延迟检测的触发只有两种：定时任务扫库（`created_at + status` 联合索引，扫「超时未支付」），或延迟消息调度（Redis ZSET 按到期时间排序，到期后再查库确认）。也就是说延迟检测自己依赖一个延迟调度设施，这个依赖要主动讲出来，不要让人以为纯流式就能做延迟检测。

扫出来的订单先查渠道再定性：渠道已扣款是回调丢失走补单，渠道无单才是用户放弃。直接把超时订单全标成异常，会把大量正常用户打进告警。

## 三、两个项目交叉

### Q13. 监控系统判定掉单后，去哪个系统查证

简历原句（两项目）：监控系统覆盖掉单检测并自动补单；回调网关负责接收验签、去重、记流水后写 Kafka。

**问题：** 两个系统的数据怎么对齐？监控系统查「这笔订单的回调到底来没来」，查什么表、用什么键？补单动作是监控系统直接写库，还是调网关？

**参考答案：**

对齐键是商户订单号加渠道通知号。监控系统的事件流里带订单号；网关的通知流水表按渠道+通知号记，表里有商户订单号字段和通知处理状态。监控系统查证时按订单号查流水：有成功记录说明回调到过网关（问题在下游处理），没有记录说明回调没到或验签被拒（问题在渠道到网关这一段）。

查证顺序构成判定依据：查网关流水 → 没有则调渠道查单 → 渠道已扣款就是回调丢失，触发补单；渠道无单就是用户未支付，进延迟观察。这个链路是「根因分析」（Q10）的确定性部分，Agent 只是在上面做汇总解释。

补单走内部接口，不直连对方数据库：监控系统调网关或支付服务暴露的带幂等的补单入口，权限边界清楚，出了问题链路可查。两个系统间用只读查询加显式接口，不搞共享表这种隐式耦合。

## 四、简历口径

### Q14. 这版写「主导从0到1」，另一版同一件事写「参与」

简历原句：主导支付订单实时监控系统从0到1的开发落地（resume04）；参与支付订单实时监控系统从0到1的开发落地（resume06）。

**问题：** 同一段工作两版动词不同，同时投出去被同一家公司对比就是诚信问题。这个项目的真实分工是什么？「主导」的证据在哪？

**参考答案：**

口径必须统一且能落地：按模块拆分。说得出口的版本是——检测引擎（窗口聚合、规则评估）、规则热加载是你写的；告警通道、值班群集成、看板是同事做的；方案评审你参与并负责技术选型。这就够撑「主导核心模块」。

两版简历的动词差异没有借口，简历库里同一件事只能有一个口径。投递记录要管理：不同版本面向不同公司时，内容主线不变，避免同一家猎头或内推渠道拿到两版。面试被问「这是你一个人做的吗」时，答分工而不是全盘揽下——揽下的版本在追问第三个细节时就会穿。

验证「主导」资格的自测：不看资料画出监控系统部署图、写出规则表结构、说出三个上线后修过的 bug。做不到，就把动词降级。

### Q15. 两版简历学校不一致：中国地质大学 vs 贵州大学

简历原句：resume04 教育经历为中国地质大学（武汉）；resume06 教育经历为贵州大学（211）。

**问题：** 同一个人两版简历两个学校，哪一个是真的？这不是措辞差异，是硬信息冲突，怎么处理？

**参考答案：**

这一条必须立即处理：确认真实学校，废掉错误的版本。教育背景是背调必查项，两版同时外流（猎头、内推群、网申系统历史记录），任何一次比对都会把所有版本一起作废，和项目写得好坏无关。

行动项：简历库逐版核对姓名、学校、毕业时间、联系方式四项硬信息，只保留一个事实口径；已投递出去的错误版本无法收回，之后的投递全部用正确版。本清单后续练习也只按正确学校那版准备学历相关追问（专业课程、校园经历）。

如果两个学校分别对应专升本/主校区分校这类真实结构，就把完整学段写清楚（本科院校与时间），而不是在两版里各写一半。

### Q16. 「单次聚合走 Lua」这句话没写完

简历原句：设计基于Redis滑动窗口的特征聚合方案（用户维度/商品维度/IP维度），窗口粒度支持1分钟~24小时，单次聚合走 Lua。

**问题：** 走 Lua 做什么？这句话在简历里断在 Lua，面试官第一反应是「然后呢」。这句话想表达的完整技术点是什么？

**参考答案：**

想表达的应该是：单次特征聚合（清理窗口外成员、写入本次事件、读取窗口计数）封装为一个 Lua 脚本原子执行，保证并发事件下计数不错乱，并省去多次网络往返。补全后的写法：「单次聚合以 Lua 脚本原子完成窗口清理、计数与读取」。

修改简历：把断句补全，或者直接删掉「单次聚合走 Lua」——Lua 是实现细节，如果面试里讲不出 Q2 那套原子性和阻塞的分析，写它反而是送题。

练习时按补全版准备：为什么三步要原子（Q2）、脚本为什么不能太重（Q1/Q2）、集群 slot 限制（Q2）。这三个追问都能接住，这句才值得写在简历上。

### Q17. 时间线：入职三个月后立项、项目间隔、以及最近半年

简历原句：工作经历 2025.07–至今；监控项目 2025.10–2025.12；回调网关 2026.03–2026.05。

**问题：** 入职头三个月在做什么？监控项目结束后到网关立项中间空了两个月？2026.05 到现在五个月在做什么？监控系统三个月「从0到1」上线日均百万级，可信吗？

**参考答案：**

三个时间点都有合理解释，但要主动准备：入职 2025.07–09 熟悉支付中台业务、参与基础能力维护（这正好对应工作经历第一条「参与中台基础支付能力建设」）；2025.12–2026.02 是监控系统上线后的观察运营期（调规则、治误报、灰度），不是空白；2026.05 之后做网关的迭代运营和可观测性建设。

「最近半年在做什么」是必问题，准备一段 30 秒版本：网关渠道扩展、监控规则运营数据（触发量、准确率变化）、可观测性改进。答不出最近半年，前面项目的可信度一起掉。

### Q18. 「了解 K8s」，了解到什么程度

简历原句：熟练在工程中使用 Git、Docker、CI/CD、Prometheus，了解K8s。

**问题：** 了解 K8s 是指什么？你的项目部署在 K8s 上吗？说一次完整的发布流程。答不上就把这个词删掉。

**参考答案：**

能撑住「了解」的最低配置：说清 Pod/Deployment/Service 的关系，一次发布是改镜像 tag 后 rollout、滚动更新、就绪探针挡流量，`kubectl logs/describe` 查过问题。再往上是加分项：Prometheus 在 K8s 里靠服务发现自动纳管 Pod，按 label 聚合实例——这能把「了解 K8s」和监控项目串成一个故事，值得准备。

如果项目实际部署在虚机或没有接触过 K8s，就删掉这个词：空词被追问一句就露底，删掉不丢分，露底丢整个面试的可信度。

简历里和这词同一条的 Prometheus 是真的（项目 Q6），所以这行的问题只在 K8s 一个词上，改起来成本最低。
