# 五项目总对比 × 我的回调网关改进清单

> 对照对象：我的支付渠道回调网关——适配器模式统一验签解密（RSA/MD5/平台证书）→ MySQL 唯一索引 + Redis 幂等 → 通知流水状态机 → 验签后立刻应答 200 → Kafka 异步分发下游 → 补偿扫描 + 状态机重放 → 下游超时与熔断。

## 1. 五项目定位速览

| 项目 | 语言 | 定位 | 回调角色 |
|---|---|---|---|
| dax-pay | Java | 聚合支付平台 | 收渠道回调 → 通知商户（与我最像的业务形态） |
| jeepay | Java | 聚合支付平台 | 收渠道回调 → 通知商户（架构最朴素可靠） |
| btcpayserver | C#/.NET | 自托管比特币支付服务器 | 业务事件 → webhook 通知（分发/重试层通用） |
| svix-webhooks | Rust | webhook 发送平台（基础设施） | 纯 outbound，webhook 全能力满配 |
| convoy | Go | 通用 webhook 网关 | inbound + outbound，与我的架构同构 |

## 2. 核心机制横向对比

### 2.1 验签与安全

| 项目 | 方案 | 防重放 | 备注 |
|---|---|---|---|
| dax-pay | 渠道官方 SDK 验签 + **URL 携带商户号**定位密钥（加密报文下唯一解法） | — | 平台侧不感知渠道差异 |
| jeepay | 渠道适配器内验签；对下游 MD5(报文+reqTime) | 弱 | 应答报文归属适配器 |
| btcpayserver | HMAC-SHA256(body) 单头 | **无** | 最简方案，可作反面教材 |
| svix | HMAC(id.timestamp.body) 三段式 + Ed25519 | **强**（时间戳容差） | 行业标杆 |
| convoy | HMAC(ts.payload) + **多 secret 版本化轮换** | 有 | 零停机换钥 |

### 2.2 入站幂等

| 项目 | 手段 |
|---|---|
| dax-pay | Redis 分布式锁 + **锁包事务**（锁释放=事务提交）+ CAS 状态机 + 终态守卫转人工 |
| jeepay | **单条 SQL 条件更新** `WHERE state='ING'`（CAS），无锁无缓存 |
| btcpayserver | delivery 记录幂等（每尝试一条，链式关联） |
| svix | msg_id 唯一键 + 队列 ack/nack at-least-once |
| convoy | EventDelivery 任务单元 + NumTrials 记账 |

→ 三种流派：**唯一索引**（我）、**条件更新 CAS**（jeepay/dax-pay）、**任务记账**（convoy/svix）。可叠加不冲突。

### 2.3 重试策略

| 项目 | 曲线 | 上限 | 特色 |
|---|---|---|---|
| dax-pay | 仿微信官方 15s/15s/30s/3m/10m/20m/30m×3/60m/3h×3/6h | 16 次 | 任务表 nextTime 扫描 + MQ 双驱动 |
| jeepay | 线性 0/30/60/90/120/150s | 6 次 | MQ 延迟消息驱动，无扫描 |
| btcpayserver | 固定序列 10s/1m/10m×7 | ~8 次 | **ShouldRetry 错误码细分**（4xx 不重试） |
| svix | 配置表 5s→10h + **±20% jitter** + 429/超时惩罚 +60s + 尊重 Retry-After | 8 档 | 延迟任务进队列 |
| convoy | `interval×2^n` 封顶 2h + 0~5s jitter | NumTrials(默认预算25) | 策略接口化、重试队列物理隔离 |

### 2.4 应答与保序

- **应答**：dax-pay/jeepay 处理完状态机再应答；jeepay 的 `shouldNotify` 三语义（success/fail/**unknown**）比我的"立刻 200"多一层表达；svix/convoy/btcpayserver 作为发送方无此问题
- **保序**：btcpayserver **按 WebhookId 串行**（端点内有序端点间并行）≈ Kafka key=端点分区；其余项目未显式保序

### 2.5 端点治理与兜底

| 能力 | 代表实现 |
|---|---|
| 自动禁用下游 | svix（宽限期+恢复）、convoy（熔断准入） |
| 投递失败主动上报 | svix operational webhook（Failing/Exhausted/Recovered/Disabled） |
| 兜底重放 | dax-pay 2 分钟扫孤儿任务、jeepay 渠道查单补单、我=补偿扫描 |
| 审计记录 | dax-pay 任务/记录分离、btcpayserver 链式 delivery、svix attempt 截断 20000B |

## 3. 我的网关：同构点验证（面试可讲）

1. **适配器统一验签** ↔ dax-pay 渠道模块化、jeepay IChannelNoticeService、convoy Source Verification——三处验证了这个抽象是行业标准做法
2. **唯一索引+Redis 双层幂等** ↔ jeepay CAS、dax-pay 锁+CAS——幂等三流派之一，且我多一层挡量设计
3. **通知流水状态机** ↔ convoy EventDelivery、jeepay MchNotifyRecord——任务粒度记账是共识
4. **验签后立刻 200 + Kafka 异步** ↔ 全部五个项目都是"快应答+异步投递"取向
5. **补偿扫描兜底** ↔ dax-pay NoticeRetryJob（几乎一样的机制，可互相印证）

## 4. 差距与改进清单（按性价比排序）

| # | 改进 | 来源 | 成本 | 收益 |
|---|---|---|---|---|
| 1 | 状态机加**终态守卫**：已终态订单收到反向成功回调不翻转、转人工 | dax-pay | 低 | 防状态倒灌资损 |
| 2 | 重试判定**错误码细分**：4xx（除408/429）不重试 | btcpayserver | 低 | 省掉无效重试 |
| 3 | 重试加 **jitter + 429/超时惩罚 + Retry-After** | svix | 低 | 防重试惊群打爆下游 |
| 4 | 出站通知**时间戳 HMAC 签名** + 多 secret 轮换预留 | svix/convoy | 中 | 下游可验真防重放 |
| 5 | 幂等更新改 **CAS 条件 UPDATE**，Redis 降级为纯挡量 | jeepay | 低 | 幂等收敛到 DB 原子层 |
| 6 | 重试走**独立 retry topic**，与首投隔离 | convoy | 中 | 重试不挤占新事件吞吐 |
| 7 | Kafka **key=下游端点**保序 | btcpayserver | 低 | 端点内事件有序 |
| 8 | 重试加 `num_trials` 上限 + 耗尽终态可人工重发 | jeepay/convoy | 低 | 防无限重放 |
| 9 | 下游连续失败**自动禁用 + 恢复探测 + 运维通知** | svix | 中 | 自动止损自愈 |
| 10 | 尝试记录存**响应摘要**（截断），控制流水膨胀 | svix | 低 | 存储可控 |

## 5. 一页话术（面试场景）

> 我调研过同类开源实现：两个支付系统（dax-pay、jeepay）验证了适配器+状态机+异步分发的方向；三个 webhook 基础设施（btcpayserver、svix、convoy）补足了我出站侧的三个短板——btcpayserver 教我按错误码决定要不要重试，svix 教我重试要加 jitter 和过载惩罚、签名要带时间戳防重放，convoy 教我把熔断做成投递前准入、签名支持密钥轮换。我的方案和它们的差异主要是量级取舍：它们为通用多租户做了端点治理和配置化策略，我在十几个渠道的规模下用唯一索引+补偿扫描就够了，这些改进点我按性价比排序，前三个改动成本很低已经吸收进设计。
